## Installation

`@ts-restless/open-api` is a library that allows you to generate OpenAPI documents from your ts-restless contracts, it's a great way to expose your API
to non-ts-rest clients - for example a public API or a client library.

<InstallTabs packageName="@ts-restless/open-api" />

## Generating an OpenAPI Document

This guide describes the v4 development source. Check a containing release before installing these changes.

The default entry requires an explicit `schemaTransformer`. It has no required validator dependency. Standard Schema supplies runtime validation, not JSON Schema conversion or OpenAPI metadata.

Choose `openApiVersion: '3.0.2'` (the default) or `'3.1.0'`. A converter must target the selected dialect: OpenAPI 3.0 schemas for 3.0.2, or JSON Schema 2020-12 for 3.1.0. Selecting a document version does not translate incompatible keywords. Incompatible dialects, unresolved references and unsupported converter combinations produce errors.

## Schema Transformers

A `SchemaTransformerSync` returns a schema object or `{ schema, required }`. `required` describes the presence of the whole value, separately from a schema object's required properties. Plain schema returns describe required values. Use `required: false` for optional or defaulted request bodies and header fields. Generation never validates an absent value to infer presence. An absent contract body or `c.noBody()` produces no request body.

Return `null` for schemas outside your converter's scope. A runtime validator with no matching conversion produces an error; type-only contracts have no runtime schema to convert. Provide a converter handling every validator used by a mixed contract.

Use `generateOpenApi` with a synchronous converter. `generateOpenApiAsync` accepts synchronous or asynchronous converters; the synchronous generator rejects promise returns. Both paths use the same document and presence rules.

### Legacy Zod 3 conversion

Install Zod 3 and the optional `@anatine/zod-openapi` peer when using the compatibility entry. Keep the existing generator name and change its import:

```typescript twoslash
import { initContract } from '@ts-restless/core';
import { z } from 'zod';
import { generateOpenApi } from '@ts-restless/open-api/legacy';

const c = initContract();
const contract = c.router({
  create: {
    method: 'POST',
    path: '/posts',
    body: z.object({ title: z.string() }),
    responses: { 204: c.noBody() },
  },
});
const document = generateOpenApi(contract, {
  info: { title: 'Posts API', version: '1.0.0' },
});
```

This deprecated compatibility entry defaults to `ZOD_3_SCHEMA_TRANSFORMER` and OpenAPI 3.0.2. The transformer is also exported from `/legacy` for explicit use with the main generator. It supports existing `@anatine/zod-openapi` metadata such as title, description and examples. Use its `extendApi(schema, metadata)` helper when adding metadata.

Zod 3 stores constant and callback defaults identically. The compatibility converter omits inferred defaults without executing either form. To document a constant default, supply it explicitly, for example `extendApi(z.string().default('draft'), { default: 'draft' })`. Runtime defaults still work when requests are validated. Required object properties and whole-body presence remain separate: a required object containing only defaulted fields still requires a body.

`mediaExamples` metadata belongs to the media type for bodies, responses and JSON query fields. It is a ts-restless metadata extension, not a JSON Schema keyword.

### Zod 4

Stable Zod 4 provides its own JSON Schema converter. Use request input schemas and response output schemas, with the target matching the document. This example supports ordinary schemas and explicitly wrapped optional bodies:

```typescript twoslash
import { z } from 'zod/v4';
import { initContract } from '@ts-restless/core';
import {
  generateOpenApi,
  type SchemaTransformerSync,
  type SchemaObject,
} from '@ts-restless/open-api';

const converter: SchemaTransformerSync = ({ schema, type, openApiVersion }) => {
  if (!(schema instanceof z.ZodType)) return null;
  return {
    schema: z.toJSONSchema(schema, {
      target: openApiVersion === '3.1.0' ? 'draft-2020-12' : 'openapi-3.0',
      io: type === 'response' ? 'output' : 'input',
    }) as SchemaObject,
    required: !(schema instanceof z.ZodOptional),
  };
};
const c = initContract();
const contract = c.router({
  create: {
    method: 'POST', path: '/posts',
    body: z.object({ title: z.string() }),
    responses: { 200: z.object({ id: z.string() }) },
  },
});
const document = generateOpenApi(contract, {
  info: { title: 'Posts API', version: '1.0.0' },
}, { schemaTransformer: converter, openApiVersion: '3.1.0' });
```

### Valibot

Install Valibot and `@valibot/to-json-schema`. Choose its native conversion target rather than passing an arbitrary JSON Schema draft through an unrelated OpenAPI converter:

```typescript twoslash
import * as v from 'valibot';
import { toJsonSchema } from '@valibot/to-json-schema';
import { initContract, isStandardSchema } from '@ts-restless/core';
import {
  generateOpenApiAsync,
  type SchemaTransformerSync,
  type SchemaObject,
} from '@ts-restless/open-api';

const converter: SchemaTransformerSync = ({ schema, openApiVersion }) => {
  if (!isStandardSchema(schema) || schema['~standard'].vendor !== 'valibot') return null;
  return {
    schema: toJsonSchema(schema as v.GenericSchema, {
      target: openApiVersion === '3.1.0' ? 'draft-2020-12' : 'openapi-3.0',
    }) as SchemaObject,
    required: (schema as v.GenericSchema).type !== 'optional',
  };
};
const c = initContract();
const contract = c.router({
  create: {
    method: 'POST', path: '/posts',
    body: v.object({ title: v.string() }),
    responses: { 204: c.noBody() },
  },
});
const document = await generateOpenApiAsync(contract, {
  info: { title: 'Posts API', version: '1.0.0' },
}, { schemaTransformer: converter });
```

These recipes deliberately leave the validator's converter responsible for unsupported transforms and defaults. Extend presence handling for other wrappers used by your contract; do not infer it by running validation. Check whether your chosen converter evaluates callback defaults, and avoid such defaults or supply an explicit conversion without evaluating them. The generator cannot undo side effects in a custom converter.

### References and parameter schemas

Root `$defs` and legacy `definitions` become `components.schemas`; document-local references are rewritten and checked, including those inside properties with names such as `default` or `x-field`. Caller-supplied component schemas are also normalized and checked against the selected dialect. Identical definitions may be shared. Conflicting definitions or titles fail instead of overwriting caller components. Convert resource IDs, external references, anchors and other JSON Schema drafts explicitly before returning them. Component names must contain only letters, digits, dots, hyphens or underscores.

Query, header and path schemas must convert to a plain object with properties. A root component reference to such an object is supported. Root unions, discriminated unions, intersections, negations and conditional field constraints (`dependentRequired`, `dependentSchemas`, `if`/`then`/`else`) fail with a route/location diagnostic because separate OpenAPI parameters cannot preserve relationships between their fields. Nested field unions remain supported. `jsonQuery` changes serialization for each field; it does not make a root union representable. For union queries, provide a deliberate documented projection or adjust the contract to ordinary object parameters.

Validate the generated document and compare generated clients when migrating, especially whole-body requiredness, nullable schemas and references. OpenAPI types now come from `openapi3-ts` 4.x; `SchemaObject`, `OpenAPIObject` and `OperationObject` are available as package type exports.

## Extending Operations with Additional OpenAPI Fields

We do not provide first-party support to set all possible OpenAPI fields on the operations such as the `security` field. In addition, you may have some specific needs to modify the fields already set by `ts-restless` such as the `tags` field.

Therefore, we have provided an `operationMapper` option to allow you to modify the OpenAPI fields of the operations. This is a callback function, that will receive the operation object, the contract endpoint, and the operation ID, and must return a valid OpenAPI operation object.
A common way to provide data to this function is to utilize the `metadata` field of the contract endpoint. However, feel free to come up with a different solution to doing this if you would not like to include this data in your contracts.

```typescript
const hasCustomTags = (
  metadata: unknown,
): metadata is { openApiTags: string[] } => {
  return (
    !!metadata && typeof metadata === 'object' && 'openApiTags' in metadata
  );
};

const hasSecurity = (
  metadata: unknown,
): metadata is { openApiSecurity: SecurityRequirementObject[] } => {
  return (
    !!metadata && typeof metadata === 'object' && 'openApiSecurity' in metadata
  );
};

const apiDoc = generateOpenApi(
  router,
  {
    info: { title: 'Blog API', version: '0.1' },
    components: {
      securitySchemes: {
        BasicAuth: {
          type: 'http',
          scheme: 'basic',
        },
      },
    },
  },
  {
    schemaTransformer: converter,
    operationMapper: (operation, appRoute, id) => ({
      ...operation,
      ...(hasCustomTags(appRoute.metadata)
        ? {
            tags: appRoute.metadata.openApiTags,
          }
        : {}),
      ...(hasSecurity(appRoute.metadata)
        ? {
            security: appRoute.metadata.openApiSecurity,
          }
        : {}),
      // You can also use the operation ID for custom logic
      description: `${operation.description || ''} (Operation: ${id})`,
    }),
  },
);
```

## Enabling `operationId`s (Recommended!)

You can set `setOperationId` to either `true` or `concatenated-path` to set `operationId`s on your endpoints.

In the case of setting it to `true`, it will use only the endpoint name from your contract. You have to ensure that the endpoint names are unique across the entire contract.

In the case of setting it to `concatenated-path`, it will use the endpoint name concatenated with the path through the nested contract.
This is useful when you have multiple endpoints with the same name but different paths. This will result in longer but more descriptive `operationId`s.

```typescript
const openApiSchema = generateOpenApi(
  postsApi,
  {
    info: {
      title: 'Posts API',
      version: '1.0.0',
    },
  },
  {
    schemaTransformer: converter,
    setOperationId: true, // [!code ++]
    // setOperationId: 'concatenated-path',
  },
);
```

Below is an example of what the OpenAPI document would look like with `operationId`'s enabled:

```typescript
{
  "openapi": "3.0.2",
  "paths": {
    "/posts": {
      "get": {
        "description": "Get all posts",
        "tags": [],
        "parameters": [
          {
            "name": "userId",
            "in": "query",
            "schema": {
              "type": "number"
            }
          }
        ],
        "operationId": "getPosts", // [!code ++]
        // or if using concatenated-path
        "operationId": "posts.getPosts", // [!code ++]
        "responses": {
```

## JSON Query Params

If you've enabled JSON Query params for your server and client, you can enable `jsonQuery` to mark the query params as `application/json` in the OpenAPI document:

```typescript
const openApiSchema = generateOpenApi(
  postsApi,
  {
    info: {
      title: 'Posts API',
      version: '1.0.0',
    },
  },
  {
    schemaTransformer: converter,
    jsonQuery: true, // [!code ++]
  },
);
```

You'll want to do this to let your non ts-restless clients know that they should send the query params as JSON.
