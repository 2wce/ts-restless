This guide describes the **ts-restless v4 development baseline**, the breaking successor to ts-rest v3. Select a containing prerelease from the [fork release notes](https://github.com/2wce/ts-restless/releases); the moving alpha tag can point to a different source baseline. Stable `4.0.0` is not published. Historical npm `0.0.0-stage` registration placeholders contain no library code and must not be installed.

Examples compile against this fork's development-checkout `@ts-restless/*` packages. See the [package migration and prerelease guide](/ts-restless-migration) for dependency replacement and release status. Existing published upstream v3 packages keep their current behavior.

## Modern validators

Keep `initContract`, `initClient` and the usual adapter setup. Use a schema that
implements Standard Schema, such as modern Zod 3, Zod 4 or Valibot. Core uses only
`~standard.validate` and Standard Schema input/output types. It does not choose a
validation path from the validator name or version.

Core and the default adapters no longer require Zod to be installed. This also
applies to their published TypeScript declarations. Validation must remain
synchronous; asynchronous schema validation is still unsupported.

## Older Zod 3

Wrap a schema that does not provide `~standard` explicitly:

```typescript twoslash
import { initContract } from '@ts-restless/core';
import { toStandardSchema } from '@ts-restless/core/legacy';
import { z } from 'zod';

const c = initContract();
const contract = c.router({
  convert: {
    method: 'POST',
    path: '/convert',
    body: toStandardSchema(z.string().transform(Number)),
    responses: { 200: toStandardSchema(z.number()) },
  },
});
```

The bridge preserves inferred input/output types, validator issue fields and Zod
object introspection. It does not change the supplied schema. Apply it to the
schema supplied to the contract; do not wrap every nested field.

For header **field records**, each field is a schema supplied directly to the
contract, so bridge each old schema that lacks `~standard`:

```typescript twoslash
import { initContract } from '@ts-restless/core';
import { toStandardSchema } from '@ts-restless/core/legacy';
import { z } from 'zod';
const c = initContract();
const contract = c.router({
  read: {
    method: 'GET', path: '/items',
    headers: { 'x-token': toStandardSchema(z.string()) },
    responses: { 200: toStandardSchema(z.object({ ok: z.boolean() })) },
  },
});
```

Bridge old schemas in `pathParams`, `query`, `body`, responses (including an
`otherResponse` body), and base/route headers. For a whole-object header schema,
bridge the object once. A modern schema that already implements `~standard`
needs no bridge. If a contract uses only types, keep `c.type<T>()` / `c.noBody()`;
these markers do not add runtime validation. Core cannot infer a runtime
validator from an arbitrary `safeParse` implementation.

An unsupported schema now throws a clear configuration error. Core no longer
automatically recognizes a `safeParse` method or silently skips that schema.
Do not work around this by casting the old schema; bridge it or upgrade its
validator. Promise-returning validation is still unsupported: use a synchronous
schema and put asynchronous checks in your application handler.

## Validation errors

Default validation errors are `StandardSchemaError`, with `name: 'ValidationError'`
and a structural `issues` array. Validator-specific fields on each issue remain
available at runtime. Treat issue paths and messages as the portable interface;
do not assume Zod-only methods such as `flatten()` or `format()` exist.

The HTTP status codes and request-error locations remain the same. Applications
that inspect `instanceof ZodError`, expect the serialized name `ZodError`, or
parse responses with the historical Zod error schemas must update those checks.
An explicitly bridged old Zod schema also uses the new default error class.

Use `TsRestResponseValidationError` from core when handling server response
validation failures. Adapter request errors expose `StandardSchemaError` in each
failed request location. Nest also exposes its existing
`TsRestResponseValidationError` for response validation.

Replace a default `instanceof ZodError` check with issue handling on the new
class. Retain a Zod-specific check only for errors your own application creates:

```typescript twoslash
import { StandardSchemaError, validationErrorResponse } from '@ts-restless/core';

function handleValidationFailure(error: unknown) {
  if (!(error instanceof StandardSchemaError)) throw error;
  const payload = validationErrorResponse(error);
  return payload.issues.map((issue) => ({
    message: issue.message,
    path: (issue.path ?? []).map((part) =>
      typeof part === 'object' ? part.key : part,
    ),
  }));
}
```

On the client, an HTTP error is JSON, not an instance of a server error class.
Update error-response schemas as well as class checks. A schema for the default
serialized validation error can be defined with your chosen validator. Here is
a typechecked Zod 3 example that accepts portable JSON issue paths and preserves
additional validator fields:

```typescript twoslash
import { z } from 'zod';

const PathPart = z.union([
  z.string(), z.number(),
  z.object({ key: z.union([z.string(), z.number()]) }).passthrough(),
]);
const ValidationErrorSchema = z.object({
  name: z.literal('ValidationError'),
  issues: z.array(z.object({
    message: z.string(),
    path: z.array(PathPart).optional(),
  }).passthrough()),
});

// For a combined Express/Fastify-style payload; use your adapter's actual envelope.
const CombinedRequestFailure = z.object({
  pathParameterErrors: ValidationErrorSchema.nullable(),
  headerErrors: ValidationErrorSchema.nullable(),
  queryParameterErrors: ValidationErrorSchema.nullable(),
  bodyErrors: ValidationErrorSchema.nullable(),
});
```

Express's default handler may return a single validation error rather than the
combined payload; Next's default handler returns the first failing location's
validation error. Nest uses `paramsResult`, `headersResult`, `queryResult` and
`bodyResult`. Serverless includes `message: 'Request validation failed'` with
the combined location fields. Preserve your adapter's envelope or custom
handler policy and replace its nested historical Zod-error schema with the
portable schema. Update any contract response declaration that describes these
errors, then test invalid parameters, headers, query and body independently.

The historical `/legacy` payload schemas require `name: 'ZodError'` and Zod issue
fields. They are useful for older payloads, but are not parsers for the new
default handlers. A `/legacy` import or explicit old-schema bridge does not enable
legacy error formatting.

## Historical helpers

These imports move out of the default core entry:

| Previous core export | Replacement |
| --- | --- |
| `ZodInferOrType`, `ZodInputOrType` | `SchemaOutputOrType`, `SchemaInputOrType` from the root for Standard Schema; historical names remain under `/legacy`. |
| `isZodType` | `isStandardSchema` for portable detection; the old Zod-only guard remains under `/legacy`. |
| `isZodObject`, `isZodObjectStrict`, `extractZodObjectShape` | Keep validator-owned introspection in your integration, or import historical Zod 3 helpers from `/legacy`. Standard Schema does not expose object fields. |
| `zodMerge` | Use field records or `combineStandardSchemas` for validating both schemas; use `/legacy` only when historical Zod object replacement semantics are required. |
| `zodErrorResponse`, `ZodErrorSchema` | `validationErrorResponse` and an application-defined portable payload schema; old payload helpers remain under `/legacy`. |
| `ResponseValidationError` | `TsRestResponseValidationError` from core for current handlers; the historical constructor remains under core `/legacy`. |
| `RequestValidationErrorSchema`, `RequestValidationErrorSchemaWithoutMessage`, `RequestValidationErrorSchemaForNest` | Define schemas matching current error payloads; historical versions remain under core `/legacy`. |
| `ContractAnyTypeLegacy` | `ContractAnyType`, after adapting old schemas. The legacy union is removed. |
| `areAllSchemasLegacyZod` | Remove the vendor-based branch. All default validation failures use `StandardSchemaError`, including bridged old schemas. |

`parseAsStandardSchema` is retained but now only returns a supplied Standard
Schema or `null`; it no longer adapts old Zod automatically. Use the explicit
bridge before passing the schema to it.

```typescript twoslash
import type { SchemaInputOrType, SchemaOutputOrType } from '@ts-restless/core';
import { toStandardSchema } from '@ts-restless/core/legacy';
import { z } from 'zod';
const numberFromString = toStandardSchema(z.string().transform(Number));
type Input = SchemaInputOrType<typeof numberFromString>; // string
type Output = SchemaOutputOrType<typeof numberFromString>; // number
```

Replace existing `@ts-restless/<package>/zod3` imports with `@ts-restless/<package>/legacy` for core, Express, Fastify, Nest, Next and serverless. The old paths are removed in this development baseline; helper names remain unchanged. Verify a containing release before changing installed package imports.

The compatibility entry points support Zod 3. Zod 4 uses the default entry
points and its own introspection/conversion tools. Fastify combines its historical helper with the native4 adapter under `/legacy`, so importing that entry requires Zod 3 even for Standard Schema contracts using another validator. Its root native5 entry remains independent of Zod. See the [Fastify migration guide](/server/fastify#fastify-4-to-5).

## Adapter error imports

| Adapter | Current default-handler error API | Historical imports available under `/legacy` |
| --- | --- | --- |
| Express | Root `RequestValidationError` contains `StandardSchemaError` in failed locations. | `DefaultRequestValidationErrorSchema`, `CombinedRequestValidationErrorSchema`. |
| Fastify | Root `RequestValidationError` contains `StandardSchemaError` in failed locations. | `RequestValidationErrorSchema`. |
| Nest | Root `TsRestRequestValidationError` / `TsRestResponseValidationError`; old short names alias these current classes. | Historical `RequestValidationError`, `ResponseValidationError`, `RequestValidationErrorSchema`. |
| Next Pages API | Root `TsRestRequestValidationError` (`RequestValidationError` aliases it); response errors use core's `TsRestResponseValidationError`. | Historical `RequestValidationError`, `RequestValidationErrorSchema`. |
| Serverless | Root `TsRestRequestValidationError` (`RequestValidationError` aliases it) and `ResponseValidationError`. | Historical `RequestValidationError`, `RequestValidationErrorSchema`. |

For example, `RequestValidationErrorSchema` moves from `@ts-rest/nest` to
`@ts-restless/nest/legacy` if you still need to describe an **old** payload. For
new handlers, catch `TsRestRequestValidationError` from `@ts-restless/nest` and
read the failed location's `issues`. A middleware filter importing the
historical constructor will not catch the new class solely because their
exported names match.

For response validation errors, preserve your adapter's existing HTTP/error
policy and read `cause.issues` on core's current response error (Nest uses its
own response error's `error.issues`). Serverless exposes its response error's
`error.issues`. Do not replace the response policy just to rename an import.

## Whole-object headers

Record-of-field-schema headers keep their route override semantics. Combining
two whole-object Standard Schemas validates both and merges successful outputs.
Both input requirements must be satisfied; the route output takes precedence.
This differs from Zod's `.merge()`, which can replace a field's validation rule.

Field-record names are normalized to lowercase before merging and validation.
Route overrides and `null` removals therefore apply regardless of casing, even
in nested routers. Client header types describe schema inputs; server header
types describe transformed outputs, with optionality inferred independently.
Change mixed-case property access in handlers to lowercase field-record names.
For transformed schemas, send the schema's input type from clients and use its
output type in handlers. Do not share a server-output type as the request type.

Whole-object schemas remain supported, including stable Zod 4 and bridged old
Zod 3 objects. Use lowercase header keys in their input and output shapes, since
HTTP adapters provide lowercase names. Their fields are not inspected or rewritten.

If an old contract relies on Zod object overrides, merge before bridging:

```typescript twoslash
import { initContract } from '@ts-restless/core';
import { toStandardSchema } from '@ts-restless/core/legacy';
import { z } from 'zod';

const baseHeaders = z.object({ role: z.literal('user') });
const routeHeaders = z.object({ role: z.literal('admin') });
const headers = toStandardSchema(baseHeaders.merge(routeHeaders));
const c = initContract();
const contract = c.router({
  read: {
    method: 'GET',
    path: '/headers',
    headers,
    responses: { 200: c.type<{ ok: boolean }>() },
  },
});
```

Supply that combined schema once, or convert headers to field records. Mixing
whole-object schemas with field records remains unsupported.

## OpenAPI

Runtime validation and JSON Schema conversion use separate boundaries. The default OpenAPI entry now requires an explicit `schemaTransformer` and supports OpenAPI 3.0.2 or 3.1.0 with a matching converter. Standard Schema validation cannot reconstruct JSON Schema or metadata.

For the existing Zod 3 converter, change the generator import to `@ts-restless/open-api/legacy` and install its optional Zod 3 and `@anatine/zod-openapi` peers. The old-Zod bridge preserves introspection. Inferred Zod 3 defaults are omitted to avoid executing callbacks; document constant defaults explicitly as OpenAPI metadata. Required bodies now emit `required: true`, including objects with all-optional fields. Optional/defaulted bodies emit `required: false`; no-body contracts omit the request body.

For Zod 4 or Valibot, select an explicit matching converter. Use `generateOpenApiAsync` for an asynchronous converter. Root query unions now produce a diagnostic instead of losing parameters. Compare generated documents and clients before deploying this migration. See the [checked OpenAPI converter examples](/openapi).

## Verify the migration

Typecheck your contracts and their clients, then exercise each invalid request
location and a response-validation failure. Check old-schema transforms,
header overrides/removals, middleware class checks and serialized issue
payloads. Generate OpenAPI if used. The [fork migration checklist](/ts-restless-migration#verify-your-application)
also covers framework upgrades and coordinated package replacement.
