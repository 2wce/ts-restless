## Usage

```typescript
import { createExpressEndpoints, initServer } from '@ts-restless/express';
import * as express from 'express';
import * as bodyParser from 'body-parser';
import { contract } from './contract';

const app = express();
app.use(bodyParser.urlencoded({ extended: false }));
app.use(bodyParser.json());

const s = initServer();
const router = s.router(contract, {
  getPost: async ({ params: { id } }) => {
    const post = prisma.post.findUnique({ where: { id } });

    return {
      status: 200,
      body: post ?? null,
    };
  },
});

createExpressEndpoints(contract, router, app);
```

`createExpressEndpoints` is a function that takes a contract, a corresponding router with implementations and middleware for each endpoint, and an express app, and it will
create the corresponding express routes for each endpoint with the correct method, paths, and middleware and attach them to your express app.

## Validated arguments and the native request

Handler arguments `params`, `query`, `body` and `headers` contain the contract's validated outputs, including transforms and defaults. The original Express `req` is passed through unchanged. Global and route middleware run before contract validation, including for invalid requests.

| Native field | Type and behavior |
| --- | --- |
| `req.params` | String path parameters inferred from the URL; optional segments can be absent. Schema transforms and defaults do not change them. |
| `req.query` | Express's parser-owned query type, including strings, arrays, nested objects or missing values. `jsonQuery` decodes only the validated handler argument. |
| `req.headers` | Native `IncomingHttpHeaders`; Node normalizes names to lowercase. Contract header transforms/defaults do not alter the raw values. |
| `req.body` | `unknown`, because it depends on the installed parser and may be absent or invalid in middleware. Narrow or validate it explicitly when raw access is required. |

Prefer the validated arguments in handlers:

```typescript twoslash
import { initContract } from '@ts-restless/core';
import { initServer } from '@ts-restless/express';
import { z } from 'zod';
const c = initContract();
const contract = c.router({
  update: {
    method: 'POST', path: '/items/:id',
    pathParams: z.object({ id: z.string().transform(Number) }),
    body: z.object({ value: z.string().transform(Number) }),
    responses: { 200: c.type<{ id: number; value: number }>() },
  },
});
const s = initServer();
// ---cut---
const router = s.router(contract, {
  update: async ({ params, body, req }) => {
    const rawId: string = req.params.id;
    const rawBody: unknown = req.body;
    return { status: 200, body: { id: params.id, value: body.value } };
  },
});
```

When upgrading from the old raw-request typing, replace transformed reads such as `req.body.value` with `body.value`, `req.query.count` with `query.count`, and transformed path/header reads with `params`/`headers`. Middleware cannot use these validated arguments; validate its raw inputs explicitly and handle missing/defaulted fields there. Revalidate only when that middleware needs its own policy, since non-idempotent transforms must not be mistaken for raw values.

The former third `TsRestRequest<T, F, S>` inference generic is removed. Prefer `TsRestRequest<typeof contract>` or `TsRestRequest<typeof contract.update>`; use the native Express `Request` generics for separately parsed requests outside this adapter. This typing correction is in development source; published alpha.3 still has the old raw-request types. Select a release containing F02 before relying on it.

## Options

You can pass an optional options object as the last argument for `createExpressEndpoints`.

```typescript
type Options = {
  logInitialization?: boolean; // print route initialization logs to console
  jsonQuery?: boolean;
  responseValidation?: boolean;
  globalMiddleware?: ((req, res, next) => void)[];
  requestValidationErrorHandler?:
    | 'default'
    | 'combined'
    | ((err: RequestValidationError, req, res, next) => void);
};
```

### Response Validation

To enable response parsing and validation, you can use the `responseValidation` option.
If a corresponding response Standard Schema is defined in the contract for the returned status code, the response will be parsed and validated.
If validation fails, a `TsRestResponseValidationError` will be thrown, causing a 500 response to be returned.

```typescript
createExpressEndpoints(contract, router, app, {
  responseValidation: true,
});
```

### Request Validation Error Handling

The default functionality of handling request validation errors is to return a 400 response with the first validation error the validator encounters.

You can pass `combined` to the `requestValidationErrorHandler` option to return a 400 response with all validation errors in the body in this form.

```typescript
{
  pathParameterErrors: StandardSchemaError | null;
  headerErrors: StandardSchemaError | null;
  queryParameterErrors: StandardSchemaError | null;
  bodyErrors: StandardSchemaError | null;
}
```

You can also pass a custom error handler function to the `requestValidationErrorHandler` option.

```typescript
createExpressEndpoints(contract, router, app, {
  requestValidationErrorHandler: (err, req, res, next) => {
    //             err is typed as ^ RequestValidationError
    res.status(400).json({
      message: 'Validation failed',
    });
  },
});
```
