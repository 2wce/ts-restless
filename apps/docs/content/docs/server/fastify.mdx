## Installation

<InstallTabs packageName="@ts-restless/fastify" />

Development source supports Fastify **5** and retains Fastify **4** as legacy/deprecated support. The first stable ts-restless v4 release will flag Fastify 4 for removal in **ts-restless v5**, after the minimum stable migration window. Use `@ts-restless/fastify` for Fastify 5 and `@ts-restless/fastify/legacy` for Fastify 4. Both entries provide the same registration API; choosing the wrong entry fails at registration with migration guidance. Published alpha.5 supports Fastify 4 only. Check the containing release before installing Fastify 5 support.

## Usage

```typescript
import Fastify from 'fastify';
import { initServer } from '@ts-restless/fastify';

const app = Fastify();

const s = initServer();

const router = s.router(contract, {
  getPost: async ({ params: { id } }) => {
    const post = await prisma.post.findUnique({ where: { id } });

    return {
      status: 200,
      body: post,
    };
  },
  createPost: async ({ body }) => {
    const post = await prisma.post.create({
      data: body,
    });

    return {
      status: 201,
      body: post,
    };
  },
});

app.register(s.plugin(router));

const start = async () => {
  try {
    await app.listen({ port: 3000 });
  } catch (err) {
    app.log.error(err);
    process.exit(1);
  }
};

start();
```

`s.registerRouter` is a function that takes a contract, a corresponding router with implementations for each route and a fastify app, and it will
create the corresponding fastify routes for each endpoint with the correct method, paths and middleware and attach them to your fastify app.

## Options

You can pass an optional options object as the last argument for `s.registerRouter`.

```typescript
type Options = {
  logInitialization?: boolean; // print route initialization logs to console
  jsonQuery?: boolean;
  responseValidation?: boolean;
  requestValidationErrorHandler?:
    | 'combined'
    | ((
        err: RequestValidationError,
        request: fastify.FastifyRequest,
        reply: fastify.FastifyReply,
      ) => void);
};
```

### Response Validation

To enable response parsing and validation, you can use the `responseValidation` option.
If there is a corresponding response Standard Schema defined in the contract for the returned status code, the response will be parsed and validated.
If validation fails a `TsRestResponseValidationError` will be thrown causing a 500 response to be returned.

```typescript
s.registerRouter(contract, router, app, {
  responseValidation: true,
});
```

### Request Validation Error Handling

The default functionality of handling request validation errors is `combined` which returns a 400 response with all validation errors in the body in this form.

```typescript
{
  pathParameterErrors: StandardSchemaError | null;
  headerErrors: StandardSchemaError | null;
  queryParameterErrors: StandardSchemaError | null;
  bodyErrors: StandardSchemaError | null;
}
```

You can also pass a custom error handler function to the `requestValidationErrorHandler` option.

```typescript
s.registerRouter(contract, router, app, {
  requestValidationErrorHandler: (err, request, reply) => {
    //             err is typed as ^ RequestValidationError
    reply.status(400).send({
      message: 'Validation failed',
    });
  },
});
```

## Fastify 4 to 5

If you stay on Fastify 4 when adopting the new package version, move every adapter value/type import to `/legacy`. This includes `initServer`, `RequestValidationError`, `RouteHooks` and implementation types. The registration API and behavior stay the same:

```diff
- import { initServer } from '@ts-restless/fastify';
+ import { initServer } from '@ts-restless/fastify/legacy';
```

The `/legacy` entry is deprecated and scheduled for removal in ts-restless v5 after the stable migration window. It requires a containing release; alpha.5 does not export it. Keep a matched earlier release if the new version is unavailable. Both native4 `/legacy` and native5 root accept Standard Schema contracts without requiring Zod.

The historical `RequestValidationErrorSchema` helper formerly exported from Fastify `/zod3` is available as the identical `RequestValidationErrorSchemaWithoutMessage` in core `/legacy`. Import it separately and alias the name if needed:

```typescript
import {
  RequestValidationErrorSchemaWithoutMessage as RequestValidationErrorSchema,
} from '@ts-restless/core/legacy';
```

Only applications using that historical helper need Zod 3 (`pnpm add zod@^3.22.3`). Its payload describes historical `ZodError` objects; importing it does not change current handlers' portable `ValidationError` payloads. Define schemas for those current errors in your chosen validator, as shown in the [Standard Schema migration guide](/standard-schema-migration#validation-errors).

To move from legacy support to Fastify 5, upgrade in this order:

1. Move your runtime to Node **20 or newer**, as required by native Fastify 5, and check each native plugin's Fastify 5 compatibility. This is Fastify's runtime requirement; ts-restless's contributor Node version is separate.
2. Select a released `@ts-restless/fastify` version whose peer range includes `^5.0.0`, together with its matching `@ts-restless/core`. This addition is currently development source; alpha.5 remains the Fastify 4 fallback. Then upgrade native `fastify` to a patched v5 release and replace `@ts-restless/fastify/legacy` value/type imports with `@ts-restless/fastify`.
3. Keep `initServer()`, `s.router`, `s.route`, `s.registerRouter` and `s.plugin`. Contracts, Standard Schema validation, route hooks, response writing and native request/reply objects retain their adapter boundary. Handlers' top-level `params`, `query`, `headers` and `body` are validated outputs; the native request retains parsed input values.
4. Replace removed Fastify metadata aliases in application hooks. Use the typed request argument's `request.routeOptions.config.tsRestRoute`; `reply.request` identifies the same native request, but native reply types do not preserve its route-specific config type. Replace Express-style `.json(...)` calls in custom validation handlers with native `.send(...)`.

```typescript
// Before, on Fastify 4: request.routeConfig.tsRestRoute
// Before, on Fastify 4: reply.context.config.tsRestRoute
const route = request.routeOptions.config.tsRestRoute;
reply.header('x-route', route.path).status(400).send({ message: 'Validation failed' });
```

If application code names `FastifyReply` with positional generic arguments, review Fastify 5's changed generic order. Prefer inferred hook/handler arguments; the adapter now derives its request/reply types from native `RouteHandlerMethod` on each major.

Follow the [native Fastify v5 migration guide](https://fastify.dev/docs/latest/Guides/Migration-Guide-V5/) for native schema compilers, logger options, redirect signature and plugin changes. ts-restless validates its contracts itself; this does not eliminate Fastify's requirements for any separate native routes or schemas you register.

The adapter installs its request-validation error handler in the registration scope. To inherit a shared parent error handler, use `s.plugin(router)` or call `s.registerRouter` inside a native plugin scope. Fastify 5 warns when an existing error handler is overridden in the same scope; review application registration order instead of suppressing that warning.

Package peer dependencies admit both native majors together; they cannot select an import path. Native types derive from the installed Fastify declarations, so compilation alone does not enforce the major. `s.registerRouter` throws on a mismatch; `s.plugin` reports it during native startup. Both checks run before installing hooks, routes or an error handler.

Before rollout, compile handlers and hooks with strict library checking and run real requests that exercise parsing/transforms, request-validation errors, declared/thrown errors, native hooks, custom response headers and no-body/text responses. The installed adapter suite verifies ESM/CommonJS types and HTTP journeys at Fastify 4.28.0 and 5.12.7 on Node 26.12.0; it does not certify every allowed patch or Node runtime.

Applications that cannot upgrade yet may keep a matched Fastify 4/package set through ts-restless v4 using `/legacy` in the new release. Legacy support keeps compatibility checks and critical security/correctness fixes. The notice/replacement window starts with stable availability, with removal no earlier than six calendar months later and targeted for ts-restless v5; there is no fixed removal date while stable v4 is unreleased.
