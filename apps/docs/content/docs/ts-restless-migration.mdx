---
title: ts-restless migration and prereleases
description: A checklist for moving from ts-rest v3 or earlier fork prereleases to ts-restless v4.
---

**ts-restless** is a maintained fork of [ts-rest](https://github.com/ts-rest/ts-rest), with contract-first, end-to-end typed REST for TypeScript. Use this page as the starting point when upgrading from upstream v3 or an earlier fork prerelease.

## Choose the release first

The first stable target is **ts-restless 4.0.0**. **`4.0.0-alpha.5` is published**, including F04 client response validation and the serverless empty-body corrections through [release PR #31](https://github.com/2wce/ts-restless/pull/31). Public npm manifests and tags for all ten libraries were checked on 2026-11-11. React 19 compatibility and Express raw-request typing first shipped in alpha.4; the TanStack Query v5-only migration, F01 Query5 compatibility and A11 shared execution first shipped in alpha.3. Alpha.2 does not contain that migration; its historical fallback guidance remains below. These guides describe development source, so check the [fork release notes](https://github.com/2wce/ts-restless/releases) for any newer feature you need. Async base headers have merged in [PR #32](https://github.com/2wce/ts-restless/pull/32) but are absent from alpha.5; their containing release is pending.

Prereleases use explicit `alpha`, `beta` or `rc` npm tags. Stable `4.0.0` is not published. On 2026-11-11, `alpha` points to alpha.5 while `latest` still points to alpha.0. Do not infer stability from `latest` or install the historical `0.0.0-stage` registration placeholders, which contain no library code. For a reproducible migration, pin the exact released version across all the ts-restless libraries you use. The moving `@alpha` tag is useful for evaluation; recheck its version when installing.

## Migration checklist

Each row identifies a removed support line, moved API or changed behavior and its replacement. Follow the rows that apply to your application before switching dependencies.

| Previous feature or support | Replacement in the v4 baseline | Migration path |
| --- | --- | --- |
| `@ts-rest/*` dependencies and imports | The matching `@ts-restless/*` packages | [Replace the complete package set](#package-migration), including shared contracts and public subpaths. |
| TypeScript `node`/`node10` or `classic` module resolution | Node16/NodeNext or Bundler; ESM and CommonJS retained | [Update compiler and tooling configuration](#typescript-module-resolution). The new resolver baseline requires a containing release; alpha.5 predates it. |
| Next.js 12, 13 or 14 | A current patched Next.js 15 or 16 release | [Upgrade Next first](#nextjs-1214), retaining your existing router integration. |
| Native Fastify 4 | Fastify 5 at root; Fastify 4 via `/legacy` through ts-restless v4 | [Move native4 imports to `/legacy`, or upgrade runtime/plugins and use root on native5](/server/fastify#fastify-4-to-5). Fastify 5 support is development source only; removal of 4 targets ts-restless v5 after the stable migration window. |
| React 16 or 17 with the React Query adapter | React 18 or 19 and matching React/DOM types | [Upgrade React before Query](/query-v5-migration#upgrade-order). React 19 also needs a containing adapter release and compatible native Query peers. |
| TanStack Query v4 in React, Vue or Solid | The framework's native Query v5 package | [Query v5 migration](/query-v5-migration), including native options, providers, status flags and pagination. |
| React root `initQueryClient`, `useTsRestQueryClient` and positional hooks | `initTsrReactQuery`, its providers, object options and `tsr.useQueryClient()` | [React API replacements](/query-v5-migration#react-api-replacements), including mutations, cache access and SSR. |
| React v4 wrapper types, `includeThrownErrorsInErrorType`, and top-level request `cache` / `next` | Inferred v5 hook/client types, an error union including `Error`, and `queryData.fetchOptions` | [Options and types](/query-v5-migration#react-options-and-types). |
| Automatic adaptation of old Zod schemas lacking `~standard` | Modern Standard Schema validators, or explicit `toStandardSchema` from `/legacy` | [Older Zod 3](/standard-schema-migration#older-zod-3), including each field in header records. |
| Zod-specific core helpers and inference types from the root | `/legacy` for historical helpers; `SchemaInputOrType` / `SchemaOutputOrType` for new code | [Moved imports and removed helpers](/standard-schema-migration#historical-helpers). |
| Historical adapter error schemas/classes from root exports | Portable default errors; historical payload helpers under the adapter's `/legacy` entry | [Exact adapter replacements](/standard-schema-migration#adapter-error-imports). Importing a compatibility helper does not restore old handler behavior. |
| `instanceof ZodError`, serialized `name: 'ZodError'`, `flatten()` / `format()` on default validation failures | `StandardSchemaError`, serialized `name: 'ValidationError'` and portable issue handling | [Validation errors and payloads](/standard-schema-migration#validation-errors). Update clients, middleware and error-response contracts together. |
| Zod whole-object header override semantics and mixed-case object fields | Validate both whole-object schemas, or merge before bridging; use lowercase whole-object fields | [Whole-object headers](/standard-schema-migration#whole-object-headers). Field records still support route overrides and `null` removals. |
| Client fetchers performing contract validation, or `c.noBody()` yielding an empty Blob | Shared client execution validates decoded results; no-body yields `undefined` | [Client response-validation migration](/client/fetch#response-validation). F04 is published in alpha.5; stop manually applying contract transforms in custom fetchers. |
| Fetcher wrappers used solely to await SSR/auth headers | Async per-request `baseHeaders` callbacks | [Dynamic headers](/client/fetch#dynamic-headers). Replace the header wrapper with callbacks; keep auth resolution in the incoming request scope. Development source only; absent from alpha.5. |
| Express `req` fields typed as validated/transformed values | Validated top-level arguments; native raw request types | [Express raw-request migration](/server/express#validated-arguments-and-the-native-request). Middleware body access needs explicit narrowing. F02 is published in alpha.4; alpha.3 retains the old types. |

There is no Query v4 `/legacy` fallback. Vue and Solid adapters remain available on v5. No Svelte adapter has been removed; applications in Svelte or any other framework can use the [plain fetch client](/client/fetch).

## Package migration

Public packages belong to the project-owned npm organization `ts-restless`, with [@2wce](https://github.com/2wce) as its initial owner.

| Upstream dependency | ts-restless dependency |
| --- | --- |
| `@ts-rest/core` | `@ts-restless/core` |
| `@ts-rest/express` | `@ts-restless/express` |
| `@ts-rest/fastify` | `@ts-restless/fastify` on native5; `@ts-restless/fastify/legacy` on native4 |
| `@ts-rest/nest` | `@ts-restless/nest` |
| `@ts-rest/next` | `@ts-restless/next` |
| `@ts-rest/serverless` | `@ts-restless/serverless` |
| `@ts-rest/react-query` | `@ts-restless/react-query` |
| `@ts-rest/open-api` | `@ts-restless/open-api` |
| `@ts-rest/solid-query` | `@ts-restless/solid-query` |
| `@ts-rest/vue-query` | `@ts-restless/vue-query` |

Replace the dependencies your application uses as a matched set, including shared contract packages, then update imports. For an Express evaluation:

```bash
pnpm remove @ts-rest/core @ts-rest/express
pnpm add @ts-restless/core@alpha @ts-restless/express@alpha
```

For a pinned evaluation, replace `@alpha` with the exact version selected from the release notes. Preserve native framework and validator dependencies; the scope change does not install or upgrade them for you. Check the lockfile for stale upstream imports in shared workspaces and for duplicated native Query packages.

Use public entry points rather than package-internal `src`, `lib` or `dist` imports. Supported subpaths include core and server adapter `/legacy`, React `/v5` and `/tanstack`, and serverless `/fetch`, `/aws`, `/azure` and `/next`. `react-query-v5` is a private implementation package; consumers use `@ts-restless/react-query`.

```typescript
import { initClient, initContract } from '@ts-restless/core';
import { toStandardSchema } from '@ts-restless/core/legacy';
import { initTsrReactQuery } from '@ts-restless/react-query';
```

## TypeScript module resolution

The stable v4 baseline uses package-export-aware resolution. `moduleResolution: "node"` (also called `"node10"`) and TypeScript's separate `"classic"` resolver are no longer supported. New packages remove `typesVersions` fallbacks and use their existing conditional `exports` to select declarations and runtime files. Some root imports might still resolve with an old resolver; that does not make it a supported configuration.

This describes development source and needs a containing release. Published alpha.5 predates this policy change; keep a matched pre-change release while preparing the configuration migration if necessary. Modern resolution does not require TypeScript7 or Node26. Use a compiler supported by your framework and capable of the selected resolver, and check your actual application; older/current pinned consumers are verified separately from every compiler version.

For an application executed directly by Node, use matching settings in `tsconfig.json`:

```json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext"
  }
}
```

Node16 with matching `module: "Node16"` and `moduleResolution: "Node16"` is also supported. These settings do not force ESM output: preserve `"type": "commonjs"` (or no `type` field) in your application package for CommonJS `.ts` files; `.cts` files also select CommonJS. Existing `require()` consumers and CommonJS builds remain supported. This change does not require a runtime upgrade solely to load ESM.

For native ESM, use `"type": "module"` in your application package or `.mts` files. Node ESM resolution requires explicit extensions on relative imports, for example `import { contract } from './contract.js'` in TypeScript source. Public package imports such as `@ts-restless/core/legacy` keep their published specifiers.

For an application whose bundler owns module loading, use:

```json
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "Bundler"
  }
}
```

Keep framework-required compiler options such as Nest's decorator metadata settings and your existing strict checks. Review inherited tsconfigs and code-generation, test-runner, ts-node and build-tool configurations so each consumer uses the intended resolver. A CommonJS Nest application can use NodeNext while preserving CommonJS output; a bundled application should follow its bundler's configuration. Do not switch to Bundler merely to bypass a direct Node runtime resolution error.

If an older compiler reports TS2742 while emitting declarations for an inferred contract or Nest handler, give the exported API a public type name rather than an internal package path. For example, name a plain response as `const helloBody: ContractPlainType<string> = c.type<string>()` (import `ContractPlainType` from `@ts-restless/core`), and annotate a Nest method with `ReturnType<typeof tsRestHandler<typeof contract>>`. The Nest9/10 fixtures verify this with TypeScript5.1.3 while preserving contract inference. A newer framework-compatible compiler can also resolve these older declaration-emission limitations. Keep declaration generation enabled when your application exports declarations.

[TypeScript6 deprecates node10 and7 removes it](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html). Setting `ignoreDeprecations` does not migrate resolution and cannot restore it on7. Enabling `skipLibCheck`, disabling package-export resolution or importing package-internal declarations is not the migration path.

Reinstall a matched package set, run your normal TypeScript check, build the application and exercise it using the real runtime/test runner. Verify the public subpaths you use, including `/legacy`, React `/v5` and serverless host entries. The old-Zod bridge and framework compatibility support remain; their legacy APIs do not require a legacy resolver. Native runtime/framework requirements still apply independently.

## Next.js 12–14

The first stable v4 baseline supports Next.js **15 and 16** through `@ts-restless/next` and `@ts-restless/serverless/next`. Next 12–14 are excluded. Use the [official Next.js upgrade guides](https://nextjs.org/docs/app/guides/upgrading) to move through the required framework upgrades before changing ts-rest packages; upgrade React and its types to the versions required by your chosen Next release.

| Existing integration | Replacement imports and guide |
| --- | --- |
| Pages Router API routes | Keep `createNextRouter` / `createNextRoute` from `@ts-restless/next`; [Pages API guide](/server/next). |
| App Router handlers | Keep `createNextHandler` from `@ts-restless/serverless/next` with `handlerType: 'app-router'`; [App Router guide](/server/serverless/next-serverless). |
| Pages Router Edge handlers | Keep `createNextHandler` with `handlerType: 'pages-router-edge'`; [Edge guide](/server/serverless/next-serverless). |

You do not need to change router style to adopt the supported Next major. Apply native framework changes from the upgrade guide, such as asynchronous request APIs where required. On Next 15 and newer, replace the removed `NextRequest.geo` / `ip` properties with the deployment provider's documented headers or helpers. For example, `nextRequest.headers.get('x-vercel-ip-country')` supplies country on deployments that provide that header; it can be absent elsewhere. Use only trusted provider headers for IP-based decisions.

Next and React Query have separate compatibility ranges. Alpha.4 supports React 18 and 19 in the public Query adapter; alpha.3 supports React 18 only. Next 16.4.2 permits React 18.2 or 19 through its native peer range. A passing Next adapter example does not certify a combined React Query application. For React 19, select alpha.4 or a newer containing release and a native Query version that also admits React 19; see [verified combinations](/query-v5-migration#upgrade-order).

## If you cannot upgrade yet

Keep a compatible version pinned while preparing the migration. These published
pre-change versions are explicit fallback points, checked against public npm
manifests on 2026-11-09:

| Requirement you still have | Pre-change release to evaluate |
| --- | --- |
| React Query v4 root API, or React16/17 | `@ts-restless/*@4.0.0-alpha.2` with native Query4; its React root still exposes the v4 wrapper. |
| Native Vue/Solid Query4 | `@ts-restless/*@4.0.0-alpha.2` with the corresponding native Query4 dependency. |
| Next12–14 | `@ts-restless/*@4.0.0-alpha.1`; its Next/serverless manifests retain those majors. Alpha.2 already narrows Next to15/16. |
| Automatic old-Zod detection or historical default Zod-error behavior | Your existing upstream `@ts-rest/*` v3 release. Fork alpha releases already use the Standard Schema defaults; `/legacy` is explicit compatibility, not an old-handler mode. |

Pin the whole used package set to the selected version and keep the matching
native peers. Existing published artifacts remain unchanged; these fallback
points do not create a new maintenance promise for obsolete native versions.
Do not bypass peer checks to treat an unsupported combination as supported.

## Retained features and current limits

Express 4/5, Nest 9–12, Fastify 4/5, the Zod 3 bridge and all ten public libraries remain in the development baseline. Fastify 5 uses the root entry; Fastify 4 uses the legacy/deprecated `/legacy` entry through ts-restless v4, with removal planned for ts-restless v5 under the stable migration policy. Alpha.5 supports Fastify 4 at root only; select a containing release for the new root/legacy split and Fastify 5 support. See the [Fastify migration guide](/server/fastify#fastify-4-to-5). React 18/19 compatibility is published from alpha.4; React 19 also requires compatible native Query peers. Peer ranges describe allowed versions; release notes identify the combinations actually tested.

The [OpenAPI Zod 3 default converter is retained](/standard-schema-migration#openapi). Changing runtime validation to Standard Schema does not automatically add JSON Schema generation for a new validator; use a matching converter when changing validators.

Some inherited APIs still carry deprecation comments: Nest's `initNestServer` and controller/request/response-shape helpers, and the plain client's top-level `cache` / `next` options. They are still present in this source baseline. Prefer [`TsRestHandler` and inferred handler types](/server/nest), and `fetchOptions.cache` / `fetchOptions.next`, respectively. Their comments are not evidence that they have already been removed from v4.

The repository's Node 26/pnpm 12 development tools are contributor requirements, not a new documented consumer runtime floor. Check native dependencies and the selected release's runtime evidence for your deployment.

## Verify your application

1. Pin a release containing your required changes, align all ts-restless packages, and install without peer mismatches. Keep the old lockfile or migration branch for rollback.
2. Run your application's TypeScript check with its normal strict settings. Check required request inputs, selected data, transformed headers and infinite-page types; do not hide migration failures with `skipLibCheck` or casts.
3. Exercise successful requests and each invalid request location. Check middleware and clients against `ValidationError` issue payloads, and test response validation failures with your configured handler policy.
4. For Query adapters, test mutation success/error, cache invalidation, a second page and a later-page failure, reactive input changes, cancellation, and hydration if you use SSR. Query errors reject response envelopes; plain `initClient` returns HTTP response envelopes for explicit status handling.
5. For Next, run the production build and exercise your actual Pages/App/Edge handler on the deployment runtime, including provider-header fallbacks.
6. Generate and compare your OpenAPI document if you publish one. Verify the converter preserves request/response schemas after any validator migration.

Migrate backend error contracts and their consuming clients together. If a temporary application-level compatibility formatter is necessary, make it explicit and test it; `/legacy` imports do not enable a legacy mode in the default adapters.
