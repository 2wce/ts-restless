## Adding support and triaging a failure

1. Record the owning package, exact installed ts-rest/native dependency versions, runtime, compiler, resolution mode and affected public import. Preserve the failing request or type consumer and compare source versus actual tarball behavior.
2. Locate the first failing boundary: native declarations/lifecycle, adapter mapping, shared contract inference/validation, transport or packaging. The integration package owns native breakage; core owns shared contract/transport behavior; build-config/package tooling owns archive/build failures. Route OpenAPI conversion to open-api and query hook/cache/reactivity failures to the relevant query package.
3. Reproduce under the promised dependency line and its applicable pinned fixture. Separate errors in upstream-native declarations from errors introduced by the adapter; do not hide either with widened casts or `skipLibCheck`.
4. Before advertising a new major/floor, require strict packed declarations and real native behavior/lifecycle tests, record resolved versions and migration examples, and decide older lines' states under the policy. Workspace success alone is insufficient. A16 will close bounded matrix/rolling-check gaps; no new automation is configured here.
5. Retire a shipped stable support promise only after an explicit notice, released verified replacement, at least six months and a major-release decision. The first stable v4 Next baseline is a separate pre-stable decision; other peer floors and fixtures remain unchanged in this inventory update.

Prereleases are published; stable publication remains disabled. Fixed grouping covers the ten explicit public libraries, with private versioning/tagging disabled by merged PR #14 and corrected for retained mixed Changesets in PR #15. Release and publication decisions remain separate. Independent adapter versioning is A17, while publication identity/readiness is [the release backlog](plans/release-readiness-backlog.md). This inventory records configured evidence and gaps; source/CI results must still be attached to each implementation slice when it is delivered.

## 2026-11-09 Query v5 baseline decision

The user chose complete Query4 removal rather than a `/legacy` bridge for the first stable fork v4. React5 becomes the default (`/v5` remains an alias), and Vue/Solid move to native5. This reduces the counted dependency-major commitments from 13 to 12: React Query4 is removed; Vue/Solid4 become5 and retain one commitment each. Framework Vue and Solid adapters remain supported. The dated demand JSON is unchanged; roughly 95% native-v5 download share is a historical decision input, not an installed-application census.

The [migration guide](../apps/docs/content/docs/query-v5-migration.mdx) records imports, peers, providers, pagination and native status/option changes. `vue-demi` is the native Vue Query bridge and a direct runtime dependency so the packaged binding shares the consumer's reactive runtime. A11 removes two policy copies; this migration also moves Solid's three query/mutation execution sites to the same core helper. Native-composition roadmap A12–A15 remains outstanding beyond this adopted execution reuse. The first containing release is `4.0.0-alpha.3`, verified against the public React/Vue/Solid npm manifests on 2026-11-10. Published alpha.2 artifacts retain their Query4 baseline and remain historical fallback points.
