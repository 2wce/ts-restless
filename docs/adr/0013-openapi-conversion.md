# Explicit OpenAPI conversion and dialects

**Status:** Accepted. **Decision recorded:** 2026-11-11.

The default OpenAPI entry requires a validator-to-schema transformer, supports explicit OpenAPI 3.0.2 and 3.1.0 targets, and has no mandatory validator dependency. The existing Zod3 converter and default generator behavior move to `/legacy`, with optional Zod3/Anatine peers. This is deprecated behavior compatibility under the established `/legacy` convention; core and adapter helpers also move to `/legacy` under [ADR0014](0014-legacy-helper-paths.md). The entry remains maintained during migration, with removal requiring a separate major-release decision and the stable notice window. Transformer results may carry whole-value presence separately from required object properties. Generation does not infer presence through runtime validation. Root query/header/path compositions and conditional field relationships that cannot preserve relationships between parameters fail with a diagnostic. Definitions are mapped into document components and references checked before returning output.

This boundary follows Standard Schema's separation of validation from conversion. It replaces the temporary OpenAPI converter exception in [ADR0001](0001-standard-schema.md); that ADR's runtime validation decisions remain unchanged. Zod3 represents constant and callback defaults identically, so the compatibility converter omits inferred defaults without running callbacks and preserves explicit constant OpenAPI metadata. Custom converters own their conversion side effects and representability. A generic silent draft translator or flattened union would produce misleading documentation and client signatures.

These are breaking migration changes within the unreleased v4 baseline, including `openapi3-ts` 4.x model types, explicit converter imports and default annotations. Public generator names and upstream attribution remain. This decision does not authorize a package version, merge or publication.
